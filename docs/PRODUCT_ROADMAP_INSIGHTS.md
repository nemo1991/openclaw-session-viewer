# 产品走向规划：洞察深化专项（v0.10+）

> 适用范围：OpenClaw Session Viewer（开源 · 本地优先 · 多源 AI 编码会话浏览器）

---

## 一、决策摘要（已与产品负责人确认）

| #   | 决策点   | 结论                                       | 影响                                                    |
| --- | -------- | ------------------------------------------ | ------------------------------------------------------- |
| D-1 | 战略重心 | **洞察深化**（让"回顾"变为"可复盘的洞察"） | 后续 1-2 个版本资源向分析/体检能力倾斜                  |

## 二、战略定位与北极星

- **一句话定位**：本地、离线、隐私安全的"多源 AI 编码会话洞察台"——不止能看，还能看出问题。
- **北极星指标（建议口径）**：**用户通过本工具主动识别并复盘的高价值会话占比**＝（被标记/被检索/被导出的异常或重点会话数）÷（可分析会话总数）。统计周期：周。目标值待埋点后定（估算基线 < 15%，目标 ≥ 40%）。
- **演进路径**：会话浏览器（已达成）→ **AI 工作流洞察台（本期）** → 团队提效平台（未来，需重新评估 D-2）。

## 三、核心举措拆解（洞察深化三大抓手）

### 抓手 1：本地分析引擎"真实化"（G2 OLAP 下沉）

**现状（事实）**：G2 Analytics 目前是前端 in-memory 纯函数聚合，已知 limitation：`retry_rate` 用 `error_count` 桶替代（非真实重试率）、subagent JSONL 未关联 parent（被当独立 session）、时间范围仅按 first/last timestamp 遮蔽。后端已有 SQLite 聚合层（`meta_aggregator` + 49 列 `session_meta`），具备下沉条件。

**目标**：把 G2 的关键聚合从前端搬到 Rust/SQLite，产出"可信任"的洞察。

| 编号  | 功能点               | 业务规则                                                                                   | 验收标准（GWT）                                                                                  |
| ----- | -------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| FR-I1 | 真实重试率           | 解析 message 顺序，标记"同 tool 失败后立即同 tool 再调用"为一次重试；按 session / 全局聚合 | Given 含 tool 失败+重试的 session，When 打开 Analytics，Then 重试率基于真实序列计算，非 error 桶 |
| FR-I2 | subagent→parent 折叠 | parser 增加 `is_subagent_root` 标记，G2 聚合时 subagent 用量/错误归并到 parent             | Given 存在 parent+subagent 会话，When 看汇总，Then 不重复计入 parent 总量                        |
| FR-I3 | 跨 source 对比维度   | Analytics 增加 `source` 维度分组（已部分支持），补齐"同模型跨 source"对比                  | Given 多 source 数据，When 选 source 维度，Then 分组正确无串源                                   |

### 抓手 2：会话体检（Session Health Check）

**目标**：从"用户自己翻"变成"系统主动标"。基于已有 `error_count` / `thinking_count` / `total_tokens` / `subagent_count` / `model_alias` 等字段，输出每会话/全局健康分与异常项。

| 编号  | 功能点        | 业务规则                                                                     | 验收标准（GWT）                                                   |
| ----- | ------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| FR-H1 | 异常会话标记  | 规则可配置（建议默认值：error≥20、token 偏离均值 3σ、subagent≥10、模型漂移） | Given 触发任一规则，When 列表/体检页展示，Then 该会话带可解释标签 |
| FR-H2 | 全局体检报告  | 首页/Graph 新增"体检"tab，汇总异常分布 + Top 风险会话                        | Given 已 sync 数据，When 打开体检，Then 展示分布图 + 可点击下钻   |
| FR-H3 | 成本/用量异常 | 基于 token 趋势识别异常飙升（参考 G2 已实现的 token trend）                  | Given 某日 token 飙升 > 基线 2×，When 体检，Then 提示"用量异常日" |

### 抓手 3：可分享的脱敏产出（强化本地优先护城河）

**目标**：让洞察"出得去"但不泄密，呼应 D-2 隐私定位。

| 编号  | 功能点       | 业务规则                                                                                | 验收标准（GWT）                                                                  |
| ----- | ------------ | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| FR-E1 | 脱敏报告导出 | 体检/会话可导出 Markdown/JSON，**路径与 PII 默认脱敏**（复用 v0.9.30 已落地的脱敏能力） | Given 含用户路径的会话，When 导出，Then 输出中路径为占位符，可一键还原需二次确认 |

## 四、关键方案选型（分析引擎）

| 方案                                  | 实现成本 | 复杂度         | 体验             | 风险             | 上线时间 | 结论                                                                  |
| ------------------------------------- | -------- | -------------- | ---------------- | ---------------- | -------- | --------------------------------------------------------------------- |
| A：下沉到现有 Rust/SQLite（**推荐**） | 低       | 低             | 好（数据已落库） | 低               | 快       | 复用 `meta_aggregator`，不加新依赖                                    |
| B：前端 in-memory 继续打补丁          | 低       | 中（逻辑散落） | 中               | 中（口径不可信） | 最快     | 备选，但口径问题无法根治                                              |
| C：引入 DuckDB/WASM                   | 高       | 高             | 好（大数椐）     | 中（~20MB 包体） | 慢       | 缓做，仅当 session 破 10k 或需 window/cube 时（参考 G2 findings S5+） |

**推荐 A**：与现有架构一致，不引入新依赖，且能根治 G2 的口径硬伤；DuckDB 留作远期。

- M1 技术债治理：抽取共享 schema / 代码生成，消除 Rust/TS 双份手写归一化（CHANGELOG 已列为已知债）。

- FR-H3 成本异常、FR-I3 跨 source 对比、FR-E1 脱敏导出。

## 八、关键假设与遗留问题

**关键假设（可推翻）**

- 目标用户仍以个人开发者为主；坚持本地优先/隐私，零上传。
- 现有 SQLite 聚合层足以支撑 v0.10–v0.11 的分析下沉，无需新存储引擎。

**遗留问题（跟踪）**

- D-2 若未来变更（如改为"开源+增值"），需重评账号/云同步架构，本规划届时失效。
- ja-JP 等国际化按 D-3 推迟至 v0.12+，i18n 资源当前仅维护 zh-CN/en-US。
- DuckDB 是否引入取决于真实会话规模，当前按"不引入"推进。
